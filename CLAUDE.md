# WhaleFollow — памятка для Claude

Аналитический агент для Polymarket: находит сильных игроков («китов»), проверяет, что их результат —
умение, а не удача, и предлагает повторять их ставки. **Ставки только виртуальные** (paper); реальная
торговля отключена (`LiveBroker` бросает исключение) и остаётся отключённой.

Пользователь пишет по-русски; интерфейс, README и итоги — на русском, простым языком.
Файл `.env` пользователя никогда не попадает в архивы и коммиты.

## Запуск и проверка
- `pip install -e ".[dev]"`, тесты: `python -m pytest -q` (≈200 тестов, ~80 с, без сети —
  синтетический мир в `tests/synthetic.py`).
- Docker: `docker compose up --build` — три процесса (`api`, `realtime`, `worker`) + шаг `migrate`, интерфейс на :8787, база в томе `/data`.
- Тесты на PostgreSQL: `WF_TEST_PG=postgresql://... python -m pytest -q` (каждая база теста — своя схема; `@pytest.mark.sqlite_only` — только SQLite).
- CLI: `whalefollow api | realtime | worker` (роли), `whalefollow run` (всё в одном), `whalefollow check`, `whalefollow alive <роль>`.
- Интерфейс: `cd frontend && npm ci && npm run check && npm run build` (сборка → `whalefollow/web`, её коммитим);
  сценарии: `WF_PYTHON=../.venv/bin/python npx playwright test` (демо-сервер `tests/demo_server.py`, без сети).

## Карта модулей (`whalefollow/`)
| Модуль | Что делает |
|---|---|
| `net.py` | Общий клиент httpx (HTTP/2, пул, таймауты, повторы 429/5xx с Retry-After, async-вариант) |
| `ingest/polymarket.py` | Клиенты Gamma / Data API v2 / CLOB (`_Http` поверх `net.py`, ограничитель-ведро), разбор рынков/сделок |
| `ingest/pipeline.py` | Загрузка сделок (дедупликация по id и по «существу» сделки), рынки, цены, split/merge |
| `players.py` | Готовые данные Polymarket: карточка игрока, форма по неделям, панель рынка (кэш 5 мин) |
| `frames.py` | Чтение в polars: `read` (курсор), `read_history` (DuckDB читает файл SQLite; иначе обычный путь); типы колонок — `SCHEMA` |
| `positions.py` | Позиции из сделок (polars): VWAP входа, выход, PnL, даты |
| `scoring/` | `metrics` (CLV, кластеры событий), `stats` (сжатие, bootstrap, тест на удачу, BH), `classify` (мейкер/инсайдер/фаворит), `sybil` (объединение кошельков), `scorer` (статусы китов; polars + numpy по игрокам, порядок генератора случайных чисел как раньше), `incremental` (отпечаток входных данных, пересчёт только изменившихся) |
| `signals/` | Копируемость сигнала (задержка, дрейф, стакан), проход по стакану |
| `decision/` | Решение (оценка кита + ИИ, запас выгоды, Келли с комиссией), лимиты и стопы |
| `execution/paper.py` | Виртуальные покупки/продажи/расчёт, портфель из fills |
| `agent.py` | Цикл: опрос/поток → склейка исполнений одной заявки → сигнал → решение |
| `streams.py`, `ws.py` | WebSocket: стаканы (CLOB market) и лента сделок (RTDS) — клиент на библиотеке websockets (sync API, потоки) |
| `rotation.py` | Ротация китов по форме: правило «в форме», недельный пересмотр без заглядывания вперёд, кривые, «держится ли форма» (Спирмен, перестановки, непересекающиеся окна) |
| `scheduler.py` | Фоновые задачи; группы fast/books — в realtime, slow/heavy — в worker; состояние — `scheduler_state()` |
| `runtime.py` | Роли процессов: пульс (`service_status`), очередь проверок (`CheckRunner`), живые цены (`QuotePublisher`) |
| `services.py` | Всё для экранов интерфейса (большой файл — читать частями по grep) |
| `api/app.py`, `api/routes.py`, `api/schemas.py`, `api/static.py`, `api/server.py` | FastAPI: вход/CSRF/заголовки (ASGI-слой), маршруты, модели pydantic, статика с ETag, SSE; `serve()` — обёртка uvicorn |
| `migrations/` | Alembic: `0001_baseline` = `schema.sql` + старые колонки; `DB.init_schema()` = upgrade head |
| `logs.py` | structlog: JSON в Docker, консоль локально, Sentry по `SENTRY_DSN` |
| `web/` | Готовая сборка интерфейса (не править руками — собирается из `frontend/`), PWA: `sw.js`, `manifest.webmanifest`, иконки |
| `frontend/` | Интерфейс: Svelte 5 + TypeScript + Vite. `src/views/` — экраны, `src/components/` — блоки (графики: `PriceChart` — lightweight-charts, `Plot` — uPlot), `src/lib/` — API, состояние, роутер, живые события, горячие клавиши, push; `public/` — sw.js, манифест, иконки; `e2e/` — сценарии Playwright |
| `push.py` | Push-уведомления (Web Push: шифрование RFC 8291, подпись VAPID), подписки устройств, отправка в фоне |
| `fees.py`, `categories.py` | Комиссии Polymarket по темам; единый список тем |
| `diagnostics.py` | Экран «Диагностика»: проверки всех API и потоков |

## Важные договорённости
- Данные собираются только по китам из списка пользователя (`tracked.py`, `auto_discover` выключен).
- Polymarket Data API — только v2 (v1 отключён, HTTP 410). Справка: `https://data-api.polymarket.com/v2/openapi.json`.
- Комиссия тейкера: `акции × ставка × p × (1−p)`, ставки по темам — в `fees.py`.
- Всё «на момент now», без заглядывания в будущее. Чек-лист ошибок — навык `trading-math-audit`.
- Выпуск версии — навык `whalefollow-release`; проверка интерфейса — навык `whalefollow-ui-check`.
- Качество: `ruff check . && ruff format --check . && mypy` (настройки в `pyproject.toml`), pre-commit, CI в `.github/workflows/ci.yml`.
- Эталон расчётов — `tests/golden` (пересоздаётся только при сознательной смене формулы: `python tests/golden/make_golden.py`).
- Схема базы меняется только новой миграцией (`alembic revision -m ...`), `schema.sql` не правится.
- Версия — в двух местах: `whalefollow/__init__.py` и `pyproject.toml`. История — разделы «Что нового» в README.

## Мажорное обновление 1.0 — план работ

**Как работать по плану.** Выполняй этапы строго по порядку, начиная с этапа 1. Этап считается
законченным, только когда выполнены все его критерии готовности. После каждого этапа:
тесты зелёные → выпуск версии (навык `whalefollow-release`: минорная версия, раздел в README, архив без `.env`)
→ короткий итог пользователю по-русски → отметь этап здесь как выполненный (`[x]`) и переходи к следующему.
Если решение необратимо или неоднозначно (удаление данных пользователя, смена формата базы без миграции,
отказ от функции) — остановись и спроси. Перед установкой нового пакета проверь, что он поддерживается
и подходит по лицензии; версии фиксируй в `pyproject.toml` / `package.json`.

Общие правила для всех этапов:
- Никакой регрессии: всё, что есть сейчас (экраны, сигналы, потоки, диагностика, вход по паролю,
  Telegram, «что было бы», рейтинг, пачечное добавление), работает и после этапа.
- Существующая база пользователя обновляется без потерь (проверять на копии реальной базы, если она есть в `/data`).
- Расчёты не меняются молча: если меняется формула — тест «было → стало» и строка в README.
- Новый код — с типами и тестами; тяжёлые модули читать частями.

### [x] Этап 1. Фундамент
> Выполнен в v0.14.0. Пользователь принял: API на 0,2–0,4 мс медленнее (цена FastAPI); Kalshi в
> «Диагностике» даёт 429 только из среды разработки (общий исходящий адрес).

1. **Сервер:** FastAPI + uvicorn вместо `api/server.py` на stdlib. Сохранить: SSE `/api/events`, gzip,
   ETag/304 для статики, вход по паролю (`auth.py`, cookie), CORS выключен по умолчанию, заголовки
   безопасности. Все маршруты из `api/routes.py`, модели запросов/ответов на pydantic, документация `/docs`.
2. **Сетевые клиенты:** httpx (async, HTTP/2, общий пул, таймауты, повторы на 429/5xx с учётом Retry-After)
   вместо requests; ограничитель частоты как сейчас (ведро жетонов, лимиты Polymarket в `util.py`).
   WebSocket — библиотека `websockets` вместо самописного `ws.py` (сохранить: переподключение с паузой,
   текстовый PING, статистику для «Диагностики», работу через HTTPS_PROXY).
3. **Миграции:** Alembic вместо `MIGRATIONS` в `db.py`; стартовая миграция = текущая схема (`schema.sql`);
   старые базы помечаются как «на стартовой версии» и дальше обновляются миграциями.
4. **Качество:** ruff (линтер + форматер), mypy (хотя бы для `scoring/`, `decision/`, `execution/`,
   `positions.py`), pre-commit, GitHub Actions: тесты + линтер на каждый push.
5. **Логи:** structlog (JSON в Docker, читаемый вид в консоли), по желанию Sentry через переменную окружения.

Готово, когда: все тесты зелёные; `docker compose up --build` поднимает приложение; `whalefollow check`
на живом Polymarket — все строки OK; экран «Диагностика» — все проверки зелёные; время ответа API
не хуже прежнего.

### [x] Этап 2. Разделение на сервисы
> Выполнен в v0.15.0: замер задержки сигнала — в README; тесты на SQLite и PostgreSQL.

1. Три процесса в `docker-compose.yml` из одного образа:
   - `api` — интерфейс, API, живые события;
   - `realtime` — агент, потоки WebSocket, сигналы (ничего тяжёлого — всегда быстрый);
   - `worker` — планировщик: рынки, цены, пересчёт китов, «что было бы», резервные копии.
2. Связь через базу; события для живого интерфейса между процессами — таблица событий или
   SQLite-уведомления (Redis не добавлять без необходимости). Проверка проверки игрока — задача для `worker`.
3. Postgres — опционально через `WF_DB_URL` (SQLite остаётся по умолчанию); тесты гонять на обеих базах в CI.
4. Состояние сервисов на экране «Диагностика» (жив ли каждый, когда последний раз работал).

Готово, когда: ночной пересчёт китов не влияет на задержку сигнала (замер до/после в README);
падение `worker` не останавливает сигналы; все тесты зелёные.

### [x] Этап 3. Аналитический движок
> Выполнен в v0.16.0: сверка с эталоном `tests/golden` (pandas 0.15) на SQLite и PostgreSQL; замеры в README;
> ротация проверена на 12 реальных китах; trading-math-audit пройден (комиссия, «идеал» в деньгах, ошибка выжившего).

1. polars (и DuckDB для запросов по истории) вместо pandas в `positions.py`, `scoring/`, `backtest/`.
   Результаты обязаны совпасть со старыми (тест-сверка на синтетическом мире и на копии реальной базы).
2. **Ротация китов по форме** (новый экран): пул китов, правило «в форме» (настраиваемое: окно, минимум
   ставок, результат, просадка), пересмотр раз в неделю. Расчёт строго без заглядывания в будущее
   (в каждый момент — только прошлые данные). Кривые: «ротация», «копировать всех», «идеал задним
   числом» (помечен как недостижимый), «случайный выбор». Главная цифра — держится ли форма
   (связь результата кита в прошлом окне и в следующем); если связи нет — экран говорит об этом прямо.
   Кривые прибыли брать готовыми из Polymarket (`players.py`).
3. Тесты-инварианты (hypothesis) для позиций, PnL, комиссий, исполнения по стакану, «что было бы».
4. Пересчёт китов — инкрементальный (только изменившиеся с прошлого раза).

Готово, когда: полный пересчёт заметно быстрее (замер в README); экран ротации работает на реальных китах;
чек-лист `trading-math-audit` пройден для нового кода.
